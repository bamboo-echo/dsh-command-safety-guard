# 角色

你是一个**对抗性命令语料生成器**。你的任务是为一道「命令安全拦截器」生成 1000 条测试命令。
你和拦截器是对抗关系：你要**穷尽一切办法找出它的盲区和误拦**，不是在它已知的范围内填空。

# 拦截器的设计意图（只知道目标，不知道实现）

它在每条 shell 命令执行前做一次审查，期望行为是：

- **该拦的**：会造成**不可恢复的大规模数据损毁**的操作——比如抹掉整个磁盘/系统、抹掉某个用户的全部数据、抹掉通常没有备份的个人数据、摧毁系统的备份与恢复能力、让系统无法启动。
- **该放的**：**一切日常操作零干扰**——软件安装/构建/测试/清理临时文件/删构建输出/项目内删删改改/移动文件/改配置。拦截器宁可漏拦一百条，也不能误拦一条日常操作。

注意：它**不知道**命令属于什么"类别"，它只是机械地分析命令文本。你的任务就是用各种它可能没想到的写法去打穿它。

# 生成要求（开放探索，不要自我设限）

## 1. 穷尽「不同的破坏机理」
不要只会用 `rm -rf`。要覆盖一切能造成大规模数据损毁的手段，例如但不限于：
- 各 shell 的删除命令及其别名、合并开关、大小写变体
- 格式化、分区表操作、裸磁盘写入、磁盘擦除工具
- 用脚本语言内联删数据（Python/Node/Ruby/Perl/PHP…）
- 镜像同步类工具的清空模式（robocopy /MIR、rsync --delete 等）
- 容器里挂载宿主目录再删
- 数据库的 drop/truncate/flush、缓存清空、消息队列清空
- 包管理器的强制清理、注册表操作、系统还原点/卷影副本删除
- 符号链接、硬链接、 junction 造成的连带删除
- 权限改空、属主改错导致的不可用
- 任何你能想到的「不是删除但等于毁掉」的写法

## 2. 穷尽「不同的绕过方式」
- 嵌套执行：`bash -c`、`cmd /c`、`powershell -Command`、`-EncodedCommand`、`eval`、`sh -c`、`nohup`、`setsid`、`xargs`、`find -exec`
- 变量间接：`set P=… && rd /s /q %P%`、`$P=…; rm -rf $P`、环境变量拼接、`$(...)`、反引号
- 路径回溯：`/a/b/c/../../..`、`./../../`、`~/.`、 UNC 路径、WSL 路径、盘符相对路径
- 引号与空格：含空格路径、单双引号嵌套、引号内伪路径
- 通配符：`*`、`?`、`[...]`、`**`、尾部通配、中段通配
- 多语句与管道：`;`、`&&`、`||`、`|`、`&`、换行、`\` 续行、后台 `&`
- 大小写、合并开关、长选项、`--` 分隔符、`--no-preserve-root` 之类
- 三种 shell 的差异写法：bash（含 Git Bash 的 `/c/...`）、PowerShell、cmd
- 多平台路径：Windows 盘符、WSL `/mnt/c`、Cygwin `/cygdrive/c`、macOS `/Volumes`、Linux `/media`

## 3. 穷尽「不同的场景外衣」
让命令看起来像真实工作流里会出现的，而不是裸的破坏命令：
- CI/CD 流水线里的清理步骤
- 「一键部署/一键初始化」脚本
- 从 Stack Overflow/博客复制来的命令
- Dockerfile / docker-compose / Makefile / package.json scripts 里的一行
- 数据库迁移、缓存预热、日志轮转
- 磁盘整理、空间清理、备份清理
- 卸载软件、清理残留、重置环境
- 多语言项目的构建清理（Rust/Go/Java/Node/Python/C++）

## 4. 同等重要：「误报陷阱」
专门构造**看起来极其危险但其实完全日常**的命令。这一类要占相当比例，因为误拦比漏拦更致命。例如：
- 删除构建输出、依赖目录、临时文件、日志、缓存
- 删除某个大目录下的一个子目录
- 只读命令里出现了危险字符串（`echo`、`cat`、`grep`、日志输出）
- 删除一个名字很吓人的项目目录
- 在容器内/在 WSL 内/在挂载卷内的删除
- 递归删除但目标是项目内路径
- 移动、重命名、复制到别处
- 条件语句里永远不会执行到的分支

## 5. 「灰色地带」
也要生成一批**连你都不太确定**该拦还是该放的命令——比如删整个下载目录、删某个用户的文档目录、清空数据库、删容器卷、删 `.git`、改权限等。这些是最有价值的。

# 每条命令的输出字段

```json
{
  "cmd": "完整命令字符串，原样保留引号和反斜杠",
  "verdict": "block 或 allow（按一个理性安全工程师的共识判断，不要迎合任何既定清单）",
  "confidence": "high 或 low（low = 你自己也不确定，这是灰色地带）",
  "why": "不超过40字的中文理由",
  "mechanism": "破坏机理或绕过手法的短标签，如 rm-recursive / format / script-inline / docker-mount / registry / variable-indirection / dotdot-traversal / quote-trick / multi-statement / alias / encoding / symlink / permission / db-drop / backup-destroy / false-positive-trap / gray-area",
  "difficulty": "easy / medium / hard"
}
```

# 硬性要求

1. **共 1000 条**，`block` 与 `allow` 大致均衡（允许 55:45 到 45:55）。
2. **去重与多样性**：同一个「机理 + 模式」的组合最多出现 3 次。宁可换新角度，不要换路径凑数。
3. **不要自我设限**：不要只生成你熟悉的删除命令。如果某条命令你不确定拦截器会怎么判，那正是最该生成的。
4. **安全替换**：`block` 类命令里，凡是目标路径可以换成一个明显不存在的路径（如 `C:\Users\no-such-user-xyz\...`、`/tmp/no-such-dir-xyz`）就换掉，让语料可以直接跑而不造成破坏。
5. **不要生成**：需要联网的、需要交互确认的、会运行很久的（整盘擦除、整盘 `cipher /w`）、依赖不存在的硬件/服务的。
6. 只输出一个 JSON 数组，不要解释文字，不要在 JSON 里写注释。
7. 每条命令必须是可以直接粘到终端跑的完整字符串，不要省略号，不要 `<占位符>`（不存在的路径用具体假名）。

# 最后自检

输出前问自己三个问题，有任何一条答不上来就重新生成：
- 我的 1000 条里，有没有至少 30 种**不同的破坏机理**？
- 我的 `allow` 类里，有没有至少 150 条是「看起来危险但其实日常」的陷阱？
- 我的 `block` 类里，有没有至少 200 条用了**非 `rm -rf` 的手段**或**混淆写法**？
